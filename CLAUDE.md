# docs-agent-platform

Docusaurus source for the WSO2 Agent Manager documentation. The product itself lives in [wso2/agent-manager](https://github.com/wso2/agent-manager); this repo only describes it.

## Documentation tasks

Use the `docs` skill (`.claude/skills/docs/`) for every documentation task: creating a page, writing or updating content, checking, style review, technical verification, CLI reference updates, and pre-merge review. Invoke it as `/docs <action> [path]` or just describe the task.

Any technical claim must be verified against the `wso2/agent-manager` source, never written from memory. `.claude/skills/docs/source.md` explains how to find a local checkout (the `AGENT_MANAGER_REPO` env var, an `am` git remote, or `../agent-manager`) and where each feature is implemented.

## Layout

- `docs/`: Next version, tracks agent-manager `main`.
- `versioned_docs/version-<v>/` and `versioned_sidebars/`: one snapshot per docs version in `versions.json`, including the hand-maintained `cloud` version.
- `sidebars.ts`: explicit sidebar; every new page must be added here.
- `docs/reference/helm-charts/`: generated by `scripts/gen-helm-reference.mjs` from the upstream charts. Do not hand-edit.

## Releases

Every merge to `main` that changes site content deploys the site (`.github/workflows/deploy.yml`; its `paths-ignore` lists the files that don't).

To cut a docs version for an agent-manager release:

1. Run the **Documentation Release** workflow (`.github/workflows/docs-release.yml`) with `version` (such as `v1.1.0`) and `docker_tag` (the agent-manager release; tag `amp/<docker_tag>` must exist). It copies `docs/` into `versioned_docs/version-<v>/`, replaces the `0.0.0-dev` placeholders, and opens a PR.
2. Before merging, push release-specific fixes to that PR's branch. In `docusaurus.config.ts`, add the version to `stsVersions` if it is an STS release, so it never becomes the default version. Add it to `unreleasedVersions` if the docs merge before the release ships: its pages are reachable by URL but stay out of the version dropdown, the announcement bar, and search. PR #45 is an example.
3. Merge the PR to publish. When the release ships, remove the version from `unreleasedVersions`.

- In `docs/`, write release versions as `v0.0.0-dev` (image tags, `amp/v0.0.0-dev` URLs) or `0.0.0-dev` (chart and bundle versions), never the upcoming release number. The cut replaces them, and fails if any remain.
- To fix content in a released version, edit `versioned_docs/version-<v>/` directly. Use the workflow's `recreate` option only for a structurally broken snapshot (bad sidebar, missing pages, failed substitution): it re-cuts from the current Next docs, so it can publish unreleased features under `<v>`.
