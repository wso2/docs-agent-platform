# On Your Environment

Install Agent Manager on an existing Kubernetes cluster with production settings: a real domain, trusted TLS, external databases, and sealed secret storage. Phase 1 installs OpenChoreo and Thunder. Phase 2 installs Agent Manager.

:::tip Evaluating?
Use the [Quick Start](../get-started/quick-start.mdx), the [k3d guide](./on-k3d.mdx), or the [VM guide](./on-a-vm.mdx) instead.
:::

:::info WSO2 subscription
With a WSO2 subscription or evaluation, you install the WSO2-supported build from `registry.wso2.com`. Select the **WSO2 Subscription** tab wherever this guide shows one. See [Install with a WSO2 Subscription](./install-with-a-wso2-subscription.mdx) for your credentials and registry project.
:::

:::info Isolation tiers
Agents run under the standard **runc** runtime. For stronger isolation, see [gVisor](./isolation-tiers/gvisor.mdx) and [Kata Containers](./isolation-tiers/kata.mdx). Both need dedicated nodes.
:::

## Before You Start

### Cluster Requirements

- Kubernetes 1.32+ with 3 nodes, each with 4 CPU cores and 8 GB RAM
- LoadBalancer support
- A default StorageClass that provisions volumes. See [Cluster Requirements](#cluster-requirements).
- Linux 6.3+ on build nodes. See [Troubleshooting](#build-pods-fail-with-mount_attr_idmap--idmap-mounts-errors) for older kernels.
- A CNI that enforces `NetworkPolicy` (recommended)

On Red Hat OpenShift, including Azure Red Hat OpenShift, also follow [Appendix: Red Hat OpenShift](#appendix-red-hat-openshift).

### Tools

| Tool | Version |
|------|---------|
| [kubectl](https://kubernetes.io/docs/tasks/tools/) | v1.32+ |
| [Helm](https://helm.sh/docs/intro/install/) | v3.12+ or Helm 4 |
| `curl`, `dig`, `openssl`, `python3` | Any recent version |

Confirm that LoadBalancers provision before you start:

```bash
kubectl create deploy lbtest --image=nginx && kubectl expose deploy lbtest --port=80 --type=LoadBalancer
kubectl wait --for=jsonpath='{.status.loadBalancer.ingress}' svc/lbtest --timeout=5m && echo "LoadBalancer OK"
kubectl delete svc/lbtest deploy/lbtest
```

You need permission to create namespaces, CRDs, ClusterRoles, Helm releases, and LoadBalancer Services.

## Plan Your Deployment

Make these decisions first. The variables below drive every later step.

### 1. Hostnames

Pick a base domain you control, such as `amp.yourdomain.com`. Every management hostname sits under it.

| Hostname | Serves | DNS target |
|---|---|---|
| `console.<base>` | Console | control-plane gateway |
| `api-amp.<base>` | API (browser, `amctl`, MCP) | control-plane gateway |
| `thunder.<base>` | Thunder login, plus `<handle>.<base>` per environment | control-plane gateway |
| `cp.<base>` | Gateway control plane (optional) | control-plane gateway |
| `traces.<base>` | Observer | observability-plane gateway |
| `*.agents.<base>` and `agents.<base>` | Deployed agents | data-plane gateway |

A single `*.<base>` wildcard record covers the control-plane hostnames and the per-environment Thunder hostnames, which are created after install. [Step 10](#step-10-publish-dns-records) lists the exact records.

Download the release bundle. Every manifest, values file, and script this guide uses comes from it:

```bash
export VERSION="0.0.0-dev"
curl -fsSL -O "https://github.com/wso2/agent-manager/releases/download/amp/v${VERSION}/wso2-agent-manager-${VERSION}.tar.gz"
tar xzf "wso2-agent-manager-${VERSION}.tar.gz"
export AMP_DIST="$PWD"
```

Set the remaining variables:

```bash
export HELM_CHART_REGISTRY="ghcr.io/wso2"
export AMP_NS="wso2-amp"
export BUILD_CI_NS="openchoreo-workflow-plane"
export OBSERVABILITY_NS="openchoreo-observability-plane"
export DEFAULT_NS="default"
export DATA_PLANE_NS="openchoreo-data-plane"
export THUNDER_NS="amp-thunder"

export BASE_DOMAIN="amp.yourdomain.com"

export CONSOLE_PUBLIC_HOST="console.${BASE_DOMAIN}"
export API_PUBLIC_HOST="api-amp.${BASE_DOMAIN}"
export THUNDER_PUBLIC_HOST="thunder.${BASE_DOMAIN}"
export CP_GW_PUBLIC_HOST="cp.${BASE_DOMAIN}"
export OBS_API_PUBLIC_HOST="traces.${BASE_DOMAIN}"
export AGENTS_DOMAIN="agents.${BASE_DOMAIN}"

export CONSOLE_PUBLIC_URL="https://${CONSOLE_PUBLIC_HOST}"
export API_PUBLIC_URL="https://${API_PUBLIC_HOST}"
export THUNDER_PUBLIC_URL="https://${THUNDER_PUBLIC_HOST}"
export OBS_API_PUBLIC_URL="https://${OBS_API_PUBLIC_HOST}"

export THUNDER_INTERNAL_URL="http://amp-thunder-extension-service.${THUNDER_NS}.svc.cluster.local:8090"

export INSTRUMENTATION_URL="http://default-default.gateway.localhost:19080/otel"
```

### 2. TLS

The main flow uses cert-manager with Let's Encrypt DNS-01. You need API credentials for the DNS provider that hosts your zone. [Step 3](#step-3-setup-tls-issuer) also covers a corporate CA. Certificate issuance needs only the zone, so it works before the gateway DNS records exist.

### 3. Decisions you cannot change later

These settings are written to a database or certificate on first boot. Changing one afterwards means uninstalling and reinstalling that component.

| Decision | Set in | Why it is frozen |
|---|---|---|
| Thunder's database (SQLite or PostgreSQL) | [Step 4](#step-4-install-thunder-extension-identity-provider) | Clients are seeded on first boot. `helm upgrade` does not re-seed. |
| Thunder's platform client secrets | [Step 4](#step-4-install-thunder-extension-identity-provider) | Same seeding job |
| `THUNDER_PUBLIC_URL`, `CONSOLE_PUBLIC_URL`, `API_PUBLIC_URL`, `OBS_API_PUBLIC_URL` | [Step 4](#step-4-install-thunder-extension-identity-provider) | Stored as the issuer, redirect URIs, and MCP resource identifiers |
| Thunder replicas > 1 | [Step 4](#step-4-install-thunder-extension-identity-provider) | Requires external PostgreSQL and a shared Redis cache |
| Agent Manager's database | [Phase 2](#phase-2-agent-manager-installation) | Switching later is a data migration |
| Environment gateway topology | [Phase 2](#phase-2-agent-manager-installation) | Role is written at first registration. Changing it means recreating the environment. |

Everything else, including OpenSearch sizing, the registry, replica counts, and isolation tiers, can change on a running platform. See the [production recommendations](./production-recommendations.mdx).

### 4. Platform secrets

Generate real values for the platform's internal OAuth clients and the OpenSearch admin:

```bash
export AMP_API_CLIENT_SECRET="$(openssl rand -hex 32)"
export AMP_SYSTEM_CLIENT_SECRET="$(openssl rand -hex 32)"
export AMP_PUBLISHER_CLIENT_SECRET="$(openssl rand -hex 32)"
export AM_OBSERVER_CLIENT_SECRET="$(openssl rand -hex 32)"
export WORKFLOW_PUBLISHER_SECRET="$(openssl rand -hex 32)"
export OBSERVER_READER_SECRET="$(openssl rand -hex 32)"
export OPENSEARCH_USERNAME="admin"
export OPENSEARCH_PASSWORD="$(openssl rand -base64 24)"
```

Keep this shell session for the whole install. Store the values in your secret manager.

:::note OTLP ingest
Agents inside the cluster can use the default `INSTRUMENTATION_URL`. For agents outside the cluster, install the API Platform Gateway extension with a public hostname (`--set gateway.vhost=https://otel.${BASE_DOMAIN}` and `--set gateway.hostname=otel.${BASE_DOMAIN}`), then set `INSTRUMENTATION_URL=https://otel.${BASE_DOMAIN}/otel`.
:::

#### Using a different secret store for deployed agents

**Optional.** Skip this if OpenBao holds everything.

Deployed agents' environment variables can live in any [External Secrets provider](https://external-secrets.io/latest/provider/aws-secrets-manager/). Add a second store next to `default`. This example uses Google Cloud Secret Manager:

```bash
kubectl apply -f - <<'EOF'
apiVersion: external-secrets.io/v1
kind: ClusterSecretStore
metadata:
  name: dataplane-secrets
spec:
  provider:
    # Replace with your provider's stanza. See the External Secrets provider docs.
    gcpsm:
      projectID: "your-project"
      auth:
        workloadIdentity:
          clusterLocation: us-central1
          clusterName: your-cluster
          serviceAccountRef:
            name: external-secrets
            namespace: external-secrets
EOF
```

Then set `secretStoreRef.name: dataplane-secrets` on the ClusterDataPlane in [Step 6](#step-6-setup-data-plane). Leave the workflow plane on `default`.

:::warning Keep `default` on OpenBao
Repointing `default` breaks two things. Git credentials are read over the Vault API, so private-repository pickers stop listing anything. The platform's seeded secrets also use KV v2 remote keys that other providers do not match, and a mismatch shows as `SecretSyncedError`.
:::

### Step 3: Setup TLS Issuer

Every gateway certificate references one ClusterIssuer named `openchoreo-ca`. Choose the tab for your certificate authority:

<Tabs groupId="tls-issuer">
  <TabItem value="letsencrypt" label="Let's Encrypt (DNS-01)" default>

Confirm the zone is delegated. The output must list your DNS provider's nameservers:

```bash
dig +short NS <your-zone> @1.1.1.1
```

Create the DNS credentials and the issuer. The example uses Route 53. Cloudflare, Google Cloud DNS, Azure DNS, and [others](https://cert-manager.io/docs/configuration/acme/dns01/) use the same structure.

```bash
kubectl create secret generic route53-credentials \
  --namespace cert-manager \
  --from-literal=secret-access-key='<AWS_SECRET_ACCESS_KEY>'

kubectl apply -f - <<EOF
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: openchoreo-ca
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ops@yourdomain.com
    privateKeySecretRef:
      name: letsencrypt-account-key
    solvers:
      - dns01:
          route53:
            region: us-east-1
            accessKeyID: <AWS_ACCESS_KEY_ID>
            secretAccessKeySecretRef:
              name: route53-credentials
              key: secret-access-key
        selector:
          dnsZones:
            - "${BASE_DOMAIN}"
EOF
```

:::tip
Use the staging server (`https://acme-staging-v02.api.letsencrypt.org/directory`) while you iterate. Production allows 5 duplicate certificates per week.
:::

### Step 4: Install Thunder Extension (Identity Provider)

Thunder handles login, API keys, and token exchange for the platform. The browser reaches it at `https://${THUNDER_PUBLIC_HOST}`.

:::danger These settings are permanent

#### Patch the service-account entitlement claim (required with Thunder ≥ 0.45)

Thunder 0.45+ puts the client name in `client_id`, but OpenChoreo 1.2.0 reads entitlements from `sub`. Without this patch, service calls return `200` with empty lists or `403`, and the gateway bootstrap fails with `Environment 'default' not found`.

```bash
patched_yaml=$(kubectl get configmap openchoreo-api-config -n openchoreo-control-plane -o yaml   | sed -E "s/claim:[[:space:]]*['\"]?sub['\"]?/claim: client_id/g")
echo "$patched_yaml" | kubectl apply --server-side --field-manager=helm --force-conflicts -f -

kubectl rollout restart deployment/openchoreo-api -n openchoreo-control-plane
kubectl rollout status deployment/openchoreo-api -n openchoreo-control-plane --timeout=120s

for binding in $(kubectl get clusterauthzrolebindings.openchoreo.dev -o jsonpath='{.items[*].metadata.name}'); do
  claim=$(kubectl get clusterauthzrolebinding.openchoreo.dev "$binding" -o jsonpath='{.spec.entitlement.claim}')
  if [ "$claim" = "sub" ]; then
    kubectl patch clusterauthzrolebinding.openchoreo.dev "$binding" --type=merge       -p '{"spec":{"entitlement":{"claim":"client_id"}}}'
  fi
done
```

Re-apply this patch after every `helm upgrade` of the Control Plane. See [After a chart upgrade](./production-recommendations.mdx#after-a-chart-upgrade).

## Appendix: Red Hat OpenShift

Agent Manager runs on Red Hat OpenShift, including managed offerings such as Azure Red Hat OpenShift (ARO). The flow is the same as the main guide; OpenShift needs extra settings at a few steps, mostly because of its stricter pod security defaults, its built-in platform components (monitoring, DNS, image registry), and the Kubernetes version a given OpenShift release ships.

This appendix was validated on **ARO, OpenShift 4.18 (Kubernetes 1.31)**.

<details>
<summary>OpenShift-specific setup and changes</summary>

Each change is tagged with where it applies:

| Tag | Applies to |
|---|---|
| **All OpenShift** | Every OpenShift cluster, any version or provider |
| **OpenShift 4.18 (Kubernetes 1.31)** | OpenShift releases that ship Kubernetes 1.31 or earlier, which is below the guide's 1.32 minimum |
| **ARO** | Azure Red Hat OpenShift only |
| **Private registry** | Clusters that push agent images to a registry requiring credentials (for example Azure Container Registry) |

Use `oc` or `kubectl` interchangeably for the commands below; the SCC commands need `oc`.

### How OpenShift security affects the install

**All OpenShift.** OpenShift admits pods through Security Context Constraints (SCCs). The default, `restricted-v2`, runs every pod as a random, namespace-assigned user ID and rejects pods that request a specific user ID, root, host access, or privilege. Most charts in this guide pin fixed non-root user IDs, and a few components need root or privilege, so you grant SCCs per namespace or service account **before** installing the charts that need them. Three built-in SCCs are used:

| SCC | Allows | Used for |
|---|---|---|
| `nonroot-v2` | Any fixed user ID except root (0) | Most platform namespaces |
| `anyuid` | Any user ID, including root | Two setup jobs that run as root |
| `privileged` | Root, privileged containers, host paths, host network | Agent build steps, the Fluent Bit log collector |

Images that expect to run as their own user (rather than OpenShift's random one) are pinned to that user through chart values in the steps below.

### Prerequisites

- **Kernel (All OpenShift).** RHCOS nodes run a 5.14 kernel, below the 6.3 needed for user-namespaced builds. Set `buildWorkflows.userNamespaces=false` on the Platform Resources chart (Phase 2, Step 4).
- **Kubernetes version (OpenShift 4.18 (Kubernetes 1.31)).** The OpenChoreo control-plane CRDs need a patch before installing; see Step 5 under Phase 1 changes below.
- **LoadBalancer check (All OpenShift).** The `nginx` image in the LoadBalancer test runs as root and is rejected by `restricted-v2`. Use the unprivileged image instead:

  ```bash
  kubectl create deploy lbtest --image=nginxinc/nginx-unprivileged:alpine --port=8080
  kubectl expose deploy lbtest --port=80 --target-port=8080 --type=LoadBalancer
  ```

- **NetworkPolicy (All OpenShift).** OpenShift's default network plugin (OVN-Kubernetes) enforces NetworkPolicy, so the platform's policies take effect. Its DNS service listens on a different port from upstream Kubernetes, which two of those policies need adjusting for (Phase 2, Steps 4 and 6).
- **Default StorageClass (ARO).** ARO ships `managed-csi` (Azure Disk) as the default class, which works as-is. Azure disks are zonal: a pod with persistent volumes can only run on a worker in its volume's zone, so keep at least one worker per zone.
- **Node count (ARO).** ARO requires 3 control-plane nodes and at least 3 workers, and does not schedule workloads on control-plane nodes. All platform components run on the workers.

### SCC grants

**All OpenShift.** Grant these before the corresponding steps. Some namespaces do not exist until a later step creates them; `oc adm policy` refuses a namespace that does not exist yet, so those are granted with a ClusterRoleBinding instead, which takes effect when the namespace is created.

```bash
for ns in openchoreo-control-plane openchoreo-data-plane openchoreo-workflow-plane openchoreo-observability-plane amp-thunder wso2-amp; do
  kubectl create namespace "$ns" --dry-run=client -o yaml | kubectl apply -f -
  oc adm policy add-scc-to-group nonroot-v2 "system:serviceaccounts:$ns"
done

oc create clusterrolebinding agent-sandbox-system-nonroot-v2 \
  --clusterrole=system:openshift:scc:nonroot-v2 \
  --group=system:serviceaccounts:agent-sandbox-system

oc create clusterrolebinding amp-thunder-default-default-nonroot-v2 \
  --clusterrole=system:openshift:scc:nonroot-v2 \
  --group=system:serviceaccounts:amp-thunder-default-default

oc adm policy add-scc-to-user anyuid -z amp-hooks -n wso2-amp
oc adm policy add-scc-to-user anyuid -z api-platform-default-default-bootstrap-sa -n openchoreo-data-plane
oc adm policy add-scc-to-user privileged -z fluent-bit -n openchoreo-observability-plane

oc create clusterrolebinding workflows-default-workflow-sa-privileged \
  --clusterrole=system:openshift:scc:privileged \
  --serviceaccount=workflows-default:workflow-sa
```

| Namespace / service account | SCC | Why |
|---|---|---|
| The four OpenChoreo plane namespaces, `amp-thunder`, `wso2-amp` | `nonroot-v2` | Pods pin fixed non-root user IDs (1000, 1001, 10001, 65532 and others) |
| `agent-sandbox-system` | `nonroot-v2` | Sandbox controller runs as user ID 1000 |
| `amp-thunder-<org>-<env>` | `nonroot-v2` | Per-environment Thunder runs as user ID 10001. Repeat for every environment you add |
| `wso2-amp/amp-hooks` | `anyuid` | The JWT key generation job runs as root |
| `openchoreo-data-plane/api-platform-default-default-bootstrap-sa` | `anyuid` | The gateway bootstrap job runs as root |
| `openchoreo-observability-plane/fluent-bit` | `privileged` | Reads node log files through host paths |
| `workflows-default/workflow-sa` | `privileged` | Agent build steps run privileged podman containers. Repeat for `workflows-<env>` of every environment you add |

### Phase 1 changes

#### Step 2: OpenBao

**All OpenShift.** The OpenBao chart pins user ID 100 by default. Add `--set global.openshift=true` to the OpenBao `helm upgrade --install` command; the chart then leaves the user ID to OpenShift and needs no SCC grant.

#### Step 5: OpenChoreo Control Plane

**OpenShift 4.18 (Kubernetes 1.31).** The control-plane chart's CRDs fail to install with `CustomResourceDefinition ... is invalid ... undefined field 'namespace'`. Some of their validation rules refer to fields named `namespace` and `var`, which Kubernetes 1.31 and earlier treat as reserved words and only accept in the escaped form `__namespace__` / `__var__`. The escaped form is also valid on newer Kubernetes.

Apply patched CRDs yourself, then install the chart with `--skip-crds`:

```bash
helm pull oci://ghcr.io/openchoreo/helm-charts/openchoreo-control-plane --version 1.2.0 --untar -d oc-cp-chart

sed -i.bak -E 's/has\(self\.var\)/has(self.__var__)/g; s/self\.scope\.namespace\)/self.scope.__namespace__)/g' \
  oc-cp-chart/openchoreo-control-plane/crds/*.yaml
rm -f oc-cp-chart/openchoreo-control-plane/crds/*.bak

kubectl apply --server-side -f oc-cp-chart/openchoreo-control-plane/crds/
```

Then add `--skip-crds` to every control-plane `helm upgrade --install` in this guide. Helm never upgrades CRDs, so on a later control-plane chart upgrade repeat these commands with the new chart version.

#### Step 8: Observability Plane

**All OpenShift.** Three changes to the observability modules:

1. **OpenSearch.** Its init container changes the data volume's owner as root, which `nonroot-v2` does not allow. The pod's `fsGroup` already makes the volume writable, so turn the init container off. Add to the logs module install:

   ```bash
   --set openSearch.persistence.enableInitChown=false
   ```

2. **Fluent Bit.** OpenShift's container runtime writes log files readable only by root, with an SELinux label unprivileged containers cannot read. The `privileged` SCC grant only permits privilege; the container must also request it. Add to the command that enables Fluent Bit:

   ```bash
   --set fluent-bit.securityContext.runAsUser=0 \
   --set fluent-bit.securityContext.runAsNonRoot=false \
   --set fluent-bit.securityContext.privileged=true \
   --set fluent-bit.securityContext.allowPrivilegeEscalation=true
   ```

   Without this, every log query in the console stays empty while all pods look healthy.

3. **Metrics module.** OpenShift ships its own Prometheus Operator and kube-state-metrics, whose cluster roles use the same names as this chart's, so the install fails with `ClusterRole "kube-state-metrics" ... exists and cannot be imported into the current release`. The chart's operator would also manage OpenShift's own `Prometheus` and `Alertmanager` resources. Rename the chart's components, keep its operator out of OpenShift's monitoring namespaces, and keep Prometheus off a public LoadBalancer. Add to the metrics module install:

   ```bash
   --set kube-prometheus-stack.prometheusOperator.fullnameOverride=openchoreo-prometheus-operator \
   --set kube-prometheus-stack.kube-state-metrics.fullnameOverride=openchoreo-kube-state-metrics \
   --set "kube-prometheus-stack.prometheusOperator.denyNamespaces={openshift-monitoring,openshift-user-workload-monitoring}" \
   --set kube-prometheus-stack.prometheus.service.type=ClusterIP
   ```

   OpenShift owns the `monitoring.coreos.com` CRDs, so the chart's operator runs against OpenShift's versions; a warning such as `unknown field "spec.enableOTLPReceiver"` during install is expected and harmless.

### Phase 2 changes

#### Step 1: Gateway Operator

**All OpenShift.** The gateway runtime image keeps its working directories owned by user ID 10001 and crash-loops (`Failed to bind to address unix:/var/run/api-platform/python-executor.sock ... Permission denied`) under OpenShift's random user ID. Pin it through the operator's gateway values. Add to the gateway operator install:

```bash
--set gateway.values.gateway.gatewayRuntime.deployment.podSecurityContext.runAsUser=10001 \
--set gateway.values.gateway.gatewayRuntime.deployment.podSecurityContext.runAsGroup=10001 \
--set gateway.values.gateway.gatewayRuntime.deployment.podSecurityContext.fsGroup=10001 \
--set gateway.values.gateway.gatewayRuntime.deployment.podSecurityContext.runAsNonRoot=true
```

Set these on the **initial** install. If the gateway extension (Step 7) is installed while the runtime is crash-looping, the operator records the gateway as permanently failed and does not retry on its own.

#### Step 2: Agent Manager

**All OpenShift.** Two components need their user ID pinned. Add to the Agent Manager install:

```bash
--set agentManagerService.podSecurityContext.runAsUser=1000 \
--set agentManagerService.podSecurityContext.runAsNonRoot=true \
--set agentManagerService.podSecurityContext.fsGroup=1000 \
--set console.securityContext.runAsUser=1001 \
--set console.securityContext.runAsNonRoot=true \
--set console.securityContext.allowPrivilegeEscalation=false \
--set "console.securityContext.capabilities.drop={ALL}"
```

- The API pod's `wait-for-db` init container (used with the in-cluster database) runs an image that defaults to root and has no user ID of its own, so the pod-level user ID applies to it.
- The console's web server writes its runtime configuration into a directory owned by user ID 1001.

#### Step 4: Platform Resources

**All OpenShift.** Add `--set buildWorkflows.userNamespaces=false` to the Platform Resources install (RHCOS kernel 5.14).

After installing, apply two patches the chart has no values for:

1. **Build checkout step.** It is the only non-privileged build step, so it runs under a random user ID with no home directory and git fails with `could not lock config file //.gitconfig`. Give it a writable `HOME`:

   ```bash
   kubectl patch clusterworkflowtemplate checkout-source --type=json \
     -p '[{"op":"add","path":"/spec/templates/0/container/env/-","value":{"name":"HOME","value":"/tmp"}}]'
   ```

2. **Agent DNS egress.** OpenShift's DNS (`openshift-dns`) listens on port **5353** behind a Service on port 53. NetworkPolicies match the pod's real port, and the agent egress policy only allows 53, so agents cannot resolve any hostname (`Temporary failure in name resolution`). Allow 5353 as well:

   ```bash
   kubectl patch componenttype.openchoreo.dev agent-api -n default --type=json \
     -p '[{"op":"add","path":"/spec/resources/0/template/spec/networkPolicy/egress/0/ports/-","value":{"port":5353,"protocol":"UDP"}},{"op":"add","path":"/spec/resources/0/template/spec/networkPolicy/egress/0/ports/-","value":{"port":5353,"protocol":"TCP"}}]'
   ```

   Agents deployed before this patch pick it up on their next deploy.

**Private registry.** Agent component types do not set `imagePullSecrets`, so agent pods cannot authenticate to a private registry themselves. On OpenShift, add the registry's credentials to the cluster-wide pull secret, which every node uses for every image:

```bash
oc get secret/pull-secret -n openshift-config -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d > cluster-pull-secret.json
jq -s '.[0] * .[1]' cluster-pull-secret.json registry-dockerconfig.json > cluster-pull-secret.merged.json
oc set data secret/pull-secret -n openshift-config --from-file=.dockerconfigjson=cluster-pull-secret.merged.json
```

`registry-dockerconfig.json` is your registry's `.dockerconfigjson` (for ACR, built from the registry's admin credentials). Keep every existing entry; on ARO the `arosvc.azurecr.io` entry must not be removed. OpenShift rolls the change out to all nodes without a reboot.

#### Step 6: Evaluation Extension

**All OpenShift.** The evaluation job's egress policy expects DNS in `kube-system` on port 53. Point it at OpenShift's DNS through chart values, adding to the evaluation extension install:

```bash
--set networkPolicy.evaluationJob.dns.namespace=openshift-dns \
--set networkPolicy.evaluationJob.dns.podLabel.key=dns.operator.openshift.io/daemonset-dns \
--set networkPolicy.evaluationJob.dns.podLabel.value=default
```

The DNS port is fixed at 53 in the chart, so add 5353 right after installing (the chart creates `workflows-default` and the policy itself):

```bash
kubectl patch networkpolicy amp-evaluation-job-egress -n workflows-default --type=json \
  -p '[{"op":"add","path":"/spec/egress/0/ports/-","value":{"port":5353,"protocol":"UDP"}},{"op":"add","path":"/spec/egress/0/ports/-","value":{"port":5353,"protocol":"TCP"}}]'
```

#### After the first agent build

**All OpenShift.** OpenShift adds an image-registry pull secret (`workflow-sa-dockercfg-...`) as the first entry in every service account's `secrets` list. Evaluation monitor workflows mount the service account's first secret as their API token, so they fail at start-up with `invalid configuration: no configuration has been provided`. Put the token Secret first:

```bash
DOCKERCFG=$(kubectl get sa workflow-sa -n workflows-default \
  -o jsonpath='{.secrets[?(@.name!="workflow-sa.service-account-token")].name}')
kubectl patch sa workflow-sa -n workflows-default --type=merge \
  -p "{\"secrets\":[{\"name\":\"workflow-sa.service-account-token\"},{\"name\":\"${DOCKERCFG}\"}]}"
```

Repeat for `workflows-<env>` of every environment you add.

#### Provision Thunder Identity Provider

**ARO.** Thunder's volumes are created in a single availability zone, and attaching them can take a few minutes on Azure. Pass `WAIT_TIMEOUT=600s` to `add-environment-thunder.sh` so the script does not stop waiting before Thunder is ready. Remember the `amp-thunder-<org>-<env>` SCC grant for every environment you add.

### After a chart upgrade

Some OpenShift changes are applied with `kubectl` on top of what Helm renders, and an upgrade of the owning chart reverts them. Re-apply after upgrading:

| Change | Owning chart | Applies to |
|---|---|---|
| Patched control-plane CRDs, install with `--skip-crds` | OpenChoreo Control Plane | OpenShift 4.18 (Kubernetes 1.31) |

## Troubleshooting

<details>
<summary>LoadBalancer has no external address</summary>

```bash
kubectl describe svc <service-name> -n <namespace>
kubectl get svc -A --field-selector spec.type=LoadBalancer
```

On EKS, confirm the AWS Load Balancer Controller is installed. On k3s, check whether Traefik holds the ports.

</details>

<details>
<summary>Certificate not issued</summary>

```bash
kubectl describe certificate <cert-name> -n <namespace>
kubectl get clusterissuers
kubectl get certificaterequests -n <namespace>
```

</details>

<details>
<summary>Plane registration fails</summary>

```bash
kubectl get clusterdataplane default -n default -o yaml
kubectl logs -n openchoreo-control-plane -l app.kubernetes.io/name=openchoreo-control-plane
```

</details>

<details>
<summary>API returns 401 for environment or gateway calls</summary>

The Control Plane's OIDC issuer does not match the `iss` claim in Thunder tokens. Compare them:

```bash
kubectl exec -n amp-thunder deploy/amp-thunder-extension-deployment -- \
  wget -qO- http://localhost:8090/.well-known/openid-configuration 2>/dev/null \
  | grep -o '"issuer":"[^"]*"'

kubectl get configmap openchoreo-api-config -n openchoreo-control-plane -o yaml | grep issuer
```

Both must match exactly. If they differ, set the Control Plane's `security.oidc.issuer` to Thunder's issuer.

</details>

<details>
<summary>Console shows "refused to connect" on login</summary>

```bash
dig +short thunder.${BASE_DOMAIN}
kubectl get httproute -n openchoreo-control-plane amp-thunder-extension
curl -s -o /dev/null -w '%{http_code}\n' https://thunder.${BASE_DOMAIN}/.well-known/openid-configuration
```

To change Thunder's public URL after install, uninstall, delete the PVC, and reinstall:

```bash
helm uninstall amp-thunder-extension -n amp-thunder
kubectl delete pvc -n amp-thunder --all
```

</details>

<details>
<summary>Evaluations fail with connection errors</summary>

The evaluation-job NetworkPolicy allows DNS egress only to `kube-system` with the `k8s-app=kube-dns` label. If your DNS runs elsewhere, such as NodeLocal DNSCache, every egress rule fails, because nothing resolves. Set `networkPolicy.evaluationJob.dns.namespace` and `podLabel` to match your DNS workload.

</details>

<details>
<summary>OpenSearch connectivity</summary>

```bash
kubectl get pods -n openchoreo-observability-plane -l app=opensearch
kubectl run -it --rm debug --image=curlimages/curl --restart=Never -- \
  curl -v http://opensearch.openchoreo-observability-plane.svc.cluster.local:9200
```

</details>

<details id="build-pods-fail-with-mount_attr_idmap--idmap-mounts-errors">
<summary>Build pods fail with MOUNT_ATTR_IDMAP or idmap errors</summary>

Build pods request a Linux user namespace (`hostUsers: false`). That needs idmapped-mount support on every mounted filesystem, and tmpfs gained it in Linux 6.3. Ubuntu 22.04 (kernel 5.15) and Amazon Linux 2 (kernel 5.10) do not have it. Errors look like this:

```
failed to create containerd container: snapshotter "overlayfs" doesn't support idmap mounts
OCI runtime create failed: ... failed to set MOUNT_ATTR_IDMAP ... invalid argument
```

Use one of these fixes:

1. **Preferred:** use build nodes with kernel 6.3 or newer.
2. Disable user namespaces with the Platform Resources chart value:

<Tabs groupId="helm-version">
  <TabItem value="helm4" label="Helm 4" default>

```bash
helm upgrade --server-side=false amp-platform-resources \
  oci://${HELM_CHART_REGISTRY}/wso2-amp-platform-resources-extension \
  --version ${VERSION} \
  --namespace ${DEFAULT_NS} \
  --reuse-values \
  --set buildWorkflows.userNamespaces=false
```

  </TabItem>
  <TabItem value="helm3" label="Helm 3">

```bash
helm upgrade amp-platform-resources \
  oci://${HELM_CHART_REGISTRY}/wso2-amp-platform-resources-extension \
  --version ${VERSION} \
  --namespace ${DEFAULT_NS} \
  --reuse-values \
  --set buildWorkflows.userNamespaces=false
```

  </TabItem>
</Tabs>

Changing containerd's `slow_chown` alone does not fix this. The build still fails on the tmpfs mount.

</details>

<details>
<summary>Agent deploys fail with "Secret does not exist" after an OpenBao restart</summary>

The guide's OpenBao dev-mode install keeps secrets in memory. Restarting `openbao-0` wipes them. Running agents keep working, but new deployments fail with `SecretSyncedError`. Re-save the agent's environment variables in the console. For production, use the persistent install from [Step 2](#step-2-set-up-the-secret-stores).

</details>

<details id="build-workflow-fails-with-cgroup-pids-error">
<summary>Build fails with a cgroup pids error (Rancher Desktop)</summary>

```
Error: OCI runtime error: crun: the requested cgroup controller `pids` is not available
```

Rancher Desktop's Lima VM does not delegate the `pids` controller to containers. Patch the three Podman-based templates to disable cgroup management. The patches require `python3` on your machine:

```bash
# gcp-buildpacks-build
kubectl get clusterworkflowtemplate gcp-buildpacks-build -o json | \
  python3 -c "
import json, sys
data = json.load(sys.stdin)
script = data['spec']['templates'][0]['container']['args'][0]
fix = '''set -e

# Fix: disable cgroup management for Podman (Rancher Desktop cgroup pids workaround)
cat > /tmp/containers.conf <<CCONF
[engine]
cgroup_manager = \"cgroupfs\"
events_logger = \"file\"
[containers]
pids_limit = 0
CCONF
export CONTAINERS_CONF=/tmp/containers.conf

'''
data['spec']['templates'][0]['container']['args'][0] = script.replace('set -e\n', fix, 1)
json.dump(data, sys.stdout)
" | kubectl apply -f -

# publish-image
kubectl get clusterworkflowtemplate publish-image -o json | \
  python3 -c "
import json, sys
data = json.load(sys.stdin)
script = data['spec']['templates'][0]['container']['args'][0]
fix = '''set -e

# Fix: disable cgroup management for Podman (Rancher Desktop cgroup pids workaround)
cat > /tmp/containers.conf <<CCONF
[engine]
cgroup_manager = \"cgroupfs\"
events_logger = \"file\"
[containers]
pids_limit = 0
CCONF
export CONTAINERS_CONF=/tmp/containers.conf

'''
data['spec']['templates'][0]['container']['args'][0] = script.replace('set -e\n', fix, 1)
json.dump(data, sys.stdout)
" | kubectl apply -f -

# amp-generate-workload
kubectl get clusterworkflowtemplate amp-generate-workload -o json | \
  python3 -c "
import json, sys
data = json.load(sys.stdin)
script = data['spec']['templates'][0]['container']['args'][0]
fix = '''# Fix: disable cgroup management for Podman (Rancher Desktop cgroup pids workaround)

[engine]

[containers]

CCONF

'''

" | kubectl apply -f -
```

Re-trigger the build. These patches are in-cluster, so reinstalling `amp-platform-resources` overwrites them. This affects Rancher Desktop only. EKS, GKE, and AKS are not affected.

</details>
