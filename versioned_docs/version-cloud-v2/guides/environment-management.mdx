# Manage Environments and Deployment Pipelines

Environments and deployment pipelines are organization-level constructs that control *where* your agents run and *how* they are promoted from one stage to the next (for example `Development → Staging → Production`).

- An **environment** represents a runtime context (e.g., `dev`, `test`, `staging`, `production`) where agents are deployed and executed.
- A **deployment pipeline** defines an ordered promotion path across those environments.
- Each **project** is assigned one deployment pipeline, and agents in that project are **promoted** along its path.

Environments and deployment pipelines are managed in WSO2 Cloud, not inside Agent Manager. They are shared by every product in your organization, so the environments you create there are the ones Agent Manager deploys agents to.

## Prerequisites

- Access to the WSO2 Cloud Console with a role that can manage environments and deployment pipelines, such as **Admin** or **Platform Engineer**. See [Access Control](../concepts/organization.mdx#access-control).

---

## Open the Organization Settings

1. Sign in to the WSO2 Cloud Console.
2. Click the app launcher (the grid of dots at the top left), then click **Settings**.

Environments and deployment pipelines are under **INFRASTRUCTURE** in the settings sidebar.

---

## Managing Environments

### View Environments

In the settings sidebar, click **Environments**. The page lists every environment with its name, description, type (**Critical** or **Non-critical**), status, and creation time. The organization's default environment is marked **Default**.

### Create an Environment

1. On the Environments page, click **Create Environment**.
2. Fill in the environment details.

   | Field | Description | Example |
   |---|---|---|
   | **Name** *(required)* | The environment's identifier. It can't be changed after the environment is created. | `staging` |
   | **Display name** *(required)* | The name shown throughout the Console. | `Staging` |
   | **Description** | An optional description. | `Pre-production testing` |
   | **Critical environment** | Turn this on for an environment that runs production-grade deployments. Deploying an agent to a critical environment requires a [separate permission](../concepts/organization.mdx#production-is-a-separate-permission). | — |

3. Click **Create**.

Agent Manager provisions the environment and installs its API Platform Gateway for
you. Once created, the new environment appears in the list.

:::note
The environment also gets its own identity service, which issues
[AgentID](../concepts/agentid.mdx) credentials to every agent deployed there. It is
provisioned and operated by WSO2. There is nothing to install or configure.
:::

### Edit an Environment

1. On the Environments page, click the edit icon on the environment's row.
2. Change the **Display name**, **Description**, or **Critical environment** setting. The **Name** can't be changed.
3. Click **Save**.

### Access the Environment ThunderID Console

Each environment has its own ThunderID instance, and that instance is what issues
[AgentID](../concepts/agentid.mdx) credentials to every agent deployed in the
environment. A few tasks are done in its console rather than in Agent Manager —
creating an OAuth application for an externally-hosted agent, for example, or
looking up an agent's application by name.

On Agent Manager Cloud the instance is provisioned and operated by WSO2. The console
URL and its administrator credentials are issued to your organization along with the
environment; ask your WSO2 administrator if you do not have them.

Day-to-day AgentID work — provisioning, viewing, rotating, and revoking a
credential — is done through Agent Manager instead, as described in
[AgentID](../concepts/agentid.mdx), so you should rarely need this console.

## Managing Deployment Pipelines

A deployment pipeline defines the promotion path agents follow across environments. 

### View Deployment Pipelines

In the settings sidebar, click **Deployment Pipelines**. Each pipeline shows its promotion flow, the number of projects that use it, and whether it is the organization's **Default** pipeline.

### Create a Deployment Pipeline

1. On the Deployment Pipelines page, click **Create Pipeline**.
2. Enter a **Name**. Use lowercase letters, numbers, and hyphens. The name can't be changed later.
3. Under **Promotion flow**, click **Add Environment** and add environments in the order agents should be promoted through them. Add at least one.
4. Click **Create**.

### View a Pipeline's Details

On the Deployment Pipelines page, click a pipeline. Its details page shows the number of environments, the projects that use it, its creation time, and its **Promotion flow**. Under **Projects**, click **Show projects** to list the projects that use the pipeline.

### Edit a Deployment Pipeline

1. On the Deployment Pipelines page, click the edit icon on the pipeline, or click **Edit** on its details page.
2. Under **Promotion flow**, add environments or remove one with its **×**. The pipeline's name can't be changed.
3. Click **Save Changes**.

Changing the promotion flow changes the path available to every agent in every project that uses the pipeline.

### Delete a Deployment Pipeline

1. On the Deployment Pipelines page, click the delete icon on the pipeline, or click **Delete** on its details page.
2. Confirm in the dialog.

:::note
You can't delete the organization's **Default** pipeline. Before deleting any other pipeline, check **Projects** on its details page and move those projects to a different pipeline (see [updating a project's deployment pipeline](#update-a-projects-deployment-pipeline)).
:::

## Update a project's deployment pipeline

Every project is assigned a deployment pipeline, which determines the environments its agents can be promoted through. You change it in the project's settings, not in the organization settings.

1. In the WSO2 Cloud Console, open the project. Its **Overview** page shows the current pipeline under **Deployment pipeline**.
2. Click **Settings**.
3. Open the **Deployment pipeline** dropdown. Each option shows the pipeline name and its promotion flow, and the organization's default pipeline is marked **Default**.
4. Select the pipeline you want and click **Save changes**.

   > A deployment pipeline is required for a project. Changing it changes the promotion path available to all agents in the project.

## Promote an agent

Promoting an agent deploys it from one environment to the next environment in the project's deployment pipeline.

1. Open the agent and go to its **Deploy** page. Each environment in the pipeline is shown as a card.
2. On the source environment's card, click **Promote**.

   > The **Promote** button appears only when the environment has a downstream target in the project's pipeline and the agent is currently **Active** in that environment.

3. In the **Promote** drawer:
   - **Target Environment** — if the source has more than one possible next environment, select the target.
   - **Configuration** — choose how the target is configured:
     - Enable **Use config from source environment** to inherit the source environment's environment variables and file mounts.
     - Leave it disabled to set environment-specific **Environment Variables** and **File Mounts** for the target environment.
4. Click **Promote**.

The same build is deployed to the target environment with the configuration you supplied. Repeat the process to advance the agent along the rest of the pipeline.
